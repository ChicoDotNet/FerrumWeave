# FerrumWeave documentation internationalization

FerrumWeave treats documentation accessibility as part of interoperability.

The project should not require native English fluency to participate in .NET language engineering. English remains the canonical documentation source so that translations have one stable semantic origin, but contributors and readers should be able to enter the project through their own language wherever practical.

## Canonical naming convention

The unsuffixed document is the canonical English source:

```text
README.md
docs/getting-started.md
docs/roadmap/template-release-plan.md
```

Translations keep the canonical basename and add a BCP-47 language tag immediately before `.md`:

```text
README.de.md
README.es.md
README.fr.md
README.it.md
README.pt-BR.md
README.ru.md
README.zh-Hans.md
README.ja.md

docs/getting-started.es.md
docs/roadmap/template-release-plan.ja.md
```

Do not translate filenames themselves. Human-facing language selectors use native language names instead of locale codes.

## Stable document identity

Documents managed by the documentation graph declare a language-independent `doc-id` and their locale in the leading metadata comment:

```html
<!--
doc-id: architecture.repository-layout
locale: en
-->
```

A translated peer keeps the same `doc-id` and adds translation provenance:

```html
<!--
doc-id: architecture.repository-layout
locale: es
translation-of: docs/architecture/repository-layout.md
source-revision: <canonical-semantic-revision>
-->
```

The `doc-id` identifies the conceptual document independently from its filename or language. This allows tooling to reason about equivalent documents without translating paths or guessing from titles.

`source-revision` tracks the canonical semantic source used for the translation. Purely generated navigation/backlink changes do not by themselves require a translation rewrite.

## Documentation graph

`tools/docgraph` is the repository-owned Rust tool that manages semantic navigation for documents carrying `doc-id` metadata.

It provides two modes:

```console
cargo run -p ferrumweave-docgraph -- render
cargo run -p ferrumweave-docgraph -- check
```

Generated regions are delimited explicitly:

```html
<!-- ferrumweave-nav:start -->
...
<!-- ferrumweave-nav:end -->

<!-- ferrumweave-backlinks:start -->
...
<!-- ferrumweave-backlinks:end -->
```

Generated regions are excluded from graph input so navigation cannot create backlink cycles. Human-authored Markdown links remain the source of graph edges.

The first managed navigation contract provides:

- a link back to the documentation home in the same locale;
- a link to the project README in the same locale;
- a localized “What links here” section derived from incoming Markdown links of the same locale.

Generated content is committed to the repository so GitHub Markdown remains useful without requiring a documentation server. Documentation graph CI runs the renderer and requires a clean `git diff`; stale generated navigation therefore fails CI with the exact required patch.

## Website routing and metadata

The GitHub Pages site is a single React application with one `index.html`. React owns locale routing, document language, title, description, canonical URL, and `hreflang` metadata.

Human-facing routes remain clean and stable:

```text
/FerrumWeave/          English
/FerrumWeave/de/       Deutsch
/FerrumWeave/es/       Español
/FerrumWeave/fr/       Français
/FerrumWeave/it/       Italiano
/FerrumWeave/pt-BR/    Português (Brasil)
/FerrumWeave/ru/       Русский
/FerrumWeave/zh-Hans/  简体中文
/FerrumWeave/ja/       日本語
```

Because GitHub Pages does not provide configurable server-side SPA rewrites, `404.html` provides the fallback. Requests for a known locale are handed back to the single React shell immediately. Genuinely unknown paths display an ox-less plow and the message “the Ox went to rest” in every currently supported documentation language, then return to the site root after five seconds.

## Translation provenance

Translated Markdown files should record their canonical source and semantic source revision in the leading metadata comment. The metadata is intentionally invisible in rendered Markdown and supports stale-translation tooling without coupling human-readable filenames to implementation details.

## Semantic rules

- Preserve technical meaning rather than translating word-for-word when that would be unnatural.
- Do not translate identifiers, commands, package names, project names, API names, code, file extensions, or compiler/runtime terminology that is normally used verbatim.
- Keep examples executable and byte-for-byte equivalent where the example itself is part of a contract.
- Translate explanatory comments inside illustrative code only when doing so cannot change the executable contract.
- Preserve warnings about unreleased or target behavior in every language.
- Prefer links to the same-language document when that translation exists; otherwise link to the canonical English source.
- English documentation remains authoritative when a translation temporarily lags behind.

## Staleness policy

A translated document may temporarily lag behind its canonical source, but this must be visible to tooling. Initially, stale translations should produce a warning rather than block unrelated engineering work. Once translation automation is mature and reliable, individual documentation surfaces may opt into stricter gates.

Generated docgraph regions are different: because they are deterministic repository state rather than human translation, they must remain current and are eligible for a blocking CI gate.

## Cultural principle

> Documentation is maintained in multiple languages because interoperability is about people, too.

FerrumWeave aims to connect Rust and .NET without forcing either ecosystem to pretend to be the other. The same principle applies to contributors: technical rigor should not be confused with native-English fluency.
