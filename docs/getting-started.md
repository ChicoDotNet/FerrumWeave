# FerrumWeave 0.1 alpha — getting started

> **R10 working contract:** this document describes the external experience FerrumWeave 0.1 alpha must certify before release. Commands that are not yet green in CI are product targets, not claims of released capability.

FerrumWeave is intended to extend normal .NET project templates with **Rust as a language choice**. The primary user experience is therefore `dotnet new <template> -lang Rust`, not a FerrumWeave-specific `dotnet new rust` project type.

The release sequence and the definition of template support are documented in [`docs/roadmap/template-release-plan.md`](roadmap/template-release-plan.md). The architectural decision is recorded in [ADR 0004](architecture/adr/0004-r10-rust-as-dotnet-template-language.md).

## Target 0.1-alpha first run

From an environment with the documented .NET and Rust prerequisites, install the FerrumWeave alpha distribution and create a normal .NET console project using Rust:

```console
dotnet new install FerrumWeave.Sdk::0.1.0-alpha.1
dotnet new console -lang Rust -n HelloFerrum
cd HelloFerrum
dotnet run
```

`FerrumWeave.Sdk` is the current package identity for the MSBuild SDK and project templates; the release must not require a second unpublished template package unless a later ADR explicitly changes that packaging decision.

The acceptance result is a Rust-authored project that builds through the normal .NET SDK workflow and reaches the causal product path:

```text
Rust source
  -> rustc
  -> FerrumWeave CodegenBackend
  -> CIL / CLR metadata
  -> CoreCLR
```

The first-run contract must work from a clean external directory where the FerrumWeave source repository is not present.

## 0.1-alpha template surface

The first alpha targets these project families:

```console
dotnet new console  -lang Rust
dotnet new classlib -lang Rust
dotnet new xunit    -lang Rust
dotnet new nunit    -lang Rust
dotnet new mstest   -lang Rust
dotnet new web      -lang Rust
dotnet new webapi   -lang Rust
```

A template is not considered supported merely because it scaffolds files. It must restore/build and complete its default meaningful workflow (`dotnet run` or `dotnet test`) through the real FerrumWeave backend, with the appropriate platform certification.

## FerrumWeave MSBuild SDK

FerrumWeave's MSBuild SDK is distributed as a NuGet SDK package. Projects generated by the templates use the versioned SDK contract, conceptually:

```xml
<Project Sdk="FerrumWeave.Sdk/0.1.0-alpha.1">
  <PropertyGroup>
    <TargetFramework>net10.0</TargetFramework>
  </PropertyGroup>
</Project>
```

Restore uses normal .NET/NuGet resolution:

```console
dotnet restore
```

The SDK package contains the FerrumWeave `Sdk.props`, `Sdk.targets`, and project-template content; consumers must not copy those files manually into their projects.

## Testing locally packed prereleases

Before public publication, a locally packed alpha may be tested by registering the directory containing the FerrumWeave `.nupkg` files as a NuGet source. A repository- or project-scoped `NuGet.Config` keeps that source local to the test workspace:

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <clear />
    <add key="ferrumweave-local" value="../artifacts/packages" />
  </packageSources>
</configuration>
```

Then use the same normal restore/build/test/run commands expected of the published package. Local package layout or maintainer-only repository knowledge must not become a hidden prerequisite for the release candidate.

## Compatibility invariant

Installing FerrumWeave must extend the template engine without hijacking existing language variants. R10 must keep commands such as these working normally:

```console
dotnet new console
dotnet new console -lang VB
dotnet new console -lang "F#"
dotnet new console -lang Rust
```

FerrumWeave's goal is to make Rust another serious .NET language choice while preserving the behavior developers already expect from the .NET SDK.
